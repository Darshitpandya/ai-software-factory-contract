# Contributing to AI Software Factory Contract

Thank you for your interest. Contributions that make the factory more correct, more usable, or more trustworthy are welcome.

## Before you start

Read the [README](README.md), particularly the [Architecture](README.md#architecture) and [Adopter Guide](README.md#adopter-guide) sections. Understand what this project is and what it deliberately excludes — a contribution that works against the core design (e.g., adding an LLM-based acceptance mechanism that replaces the verifier) will not be merged.

## Ground rules

1. **No fabricated evidence.** Tests must actually run. Benchmark numbers must come from real execution. Do not invent run IDs, approval records, or scan results.
2. **No hardcoded credentials.** All secrets go through runtime injection. Any PR containing a credential key or value is immediately rejected.
3. **Definition of done.** A change is complete when `pnpm typecheck`, `pnpm lint`, `pnpm test`, and `pnpm factory registry:verify` all exit 0. Provide the commands and exit codes in your PR description.
4. **Schema changes need migration.** A change to any file in `contracts/schemas/` requires a matching migration in `db/migrations/` and a version bump in the affected schema's `$id`.
5. **Factory release changes need evaluation.** A PR that changes `factory-releases/1.x.y/factory-release.yaml` or any `SKILL.md` must include `skills.lock.json` regenerated by `pnpm lock-components`. Model or sandbox changes additionally require an evaluation run before promotion.

## How to contribute

### Bug reports

Open an issue with:
- Which command failed and what you ran exactly
- Full terminal output (redact any secret values)
- Node.js version (`node --version`), pnpm version (`pnpm --version`), OS
- Operating profile (`local-dev` / `ci-integration`)

### Feature requests

Open an issue first. Describe the problem you are trying to solve, not the solution. If the feature affects a schema, an acceptance check, or the factory release model, describe the impact on existing WorkOrders and runs.

### Pull requests

1. Fork the repo and create a branch from `main`
2. Make your change
3. Run the full check suite:
   ```bash
   pnpm typecheck
   pnpm lint
   pnpm test
   pnpm factory registry:verify
   ```
4. If you changed any factory stage script (`verify-*.ts`), add or update the corresponding negative fixture test
5. Write a clear PR description: what problem it solves, what changed, what you tested
6. Do not modify `factory-releases/active.yaml` in a feature PR

### Skill contributions

Skills (`SKILL.md`) define the procedures each factory stage follows. To add or update a skill:

1. Edit or create the `SKILL.md` in `factories/<stage>/skills/<skill-name>/SKILL.md`
2. Run `pnpm lock-components` to update `factory-releases/skills.lock.json`
3. Add a positive test fixture (happy path) and a negative test fixture (required failure case) under `factories/<stage>/tests/`
4. Document the `Authority boundary` section accurately — the skill must not claim approval authority

### New factory stage (rare)

The five stages are intentional. Adding a sixth requires:
- An architecture decision record (`adr-*.md`) explaining why five is insufficient
- A schema change to `factory-run.schema.json` (new stage name in `FactoryStage` enum)
- A new entry in `FACTORY_STAGES` in `packages/contract-types/src/index.ts`
- A complete `AGENTS.md`, at least one `SKILL.md`, a `verify-<stage>.ts` script, and a `workflow.yaml`
- An evaluation run comparing a factory release with and without the new stage

## Code style

- TypeScript strict mode; no `any` without a comment explaining why
- No `console.log` in library packages (use the telemetry package)
- Functions that call external APIs go behind a typed adapter in `packages/`
- Tests go next to the code they test, not in a top-level `test/` folder (exception: stage fixture tests in `factories/<stage>/tests/`)

## Questions

Open a GitHub Discussion or an issue tagged `question`. Do not open an issue to ask how to use the factory for your specific use case — read the [Adopter Guide](README.md#adopter-guide) first.
